# 关键维度对比与决策

## 概述

本文档通过横向对比不同架构的核心特征,揭示架构选择背后的权衡本质,为架构选型提供决策依据。

---

## 1. 传统 MVC vs Clean/六边形

### 1.1 依赖方向的根本差异

**传统 MVC/分层架构**:
- **依赖方向**: 从上到下,业务逻辑层依赖数据访问层
- **典型结构**: Controller → Service(业务逻辑) → Repository(数据访问) → Database
- **问题**: 业务逻辑被"污染",必须知道持久化细节(如 JPA 注解)

**Clean/六边形架构**:
- **依赖方向**: 从外到内,外层依赖内层,内层不知道外层
- **典型结构**: 业务逻辑定义接口(Port),外层实现接口(Adapter)
- **优势**: 业务逻辑纯粹,不依赖任何技术细节

### 1.2 对可测试性的影响

| 维度 | 传统架构 | 端口驱动架构 |
|------|---------|------------|
| 单元测试 | 必须 Mock 数据库或使用测试数据库 | 可以用内存实现替代,无需 Mock |
| 测试速度 | 慢(依赖外部系统) | 快(纯内存) |
| 测试隔离性 | 差(多个测试可能互相影响) | 好(完全隔离) |
| 测试覆盖率 | 难以达到高覆盖率 | 容易达到高覆盖率 |

**示例对比**:

传统架构测试:
```java
@Test
public void testTransfer() {
    // 必须准备测试数据库
    testDatabase.insert(account1);
    testDatabase.insert(account2);
    
    service.transfer(account1, account2, 100);
    
    // 从数据库查询验证
    assertEquals(900, testDatabase.getBalance(account1));
}
```

端口驱动架构测试:
```java
@Test
public void testTransfer() {
    // 使用内存实现,无需数据库
    InMemoryAccountRepository repo = new InMemoryAccountRepository();
    repo.save(account1);
    repo.save(account2);
    
    TransferUseCase useCase = new TransferUseCase(repo);
    useCase.execute(account1Id, account2Id, 100);
    
    // 直接验证领域对象状态
    assertEquals(900, repo.findById(account1Id).getBalance());
}
```

### 1.3 对可维护性的影响

**传统架构的典型问题**:
- 更换数据库(如从 MySQL 到 MongoDB)需要修改业务逻辑
- 更换框架(如从 Spring 到 Quarkus)影响业务代码
- 业务逻辑与技术细节交织,难以理解和修改

**端口驱动架构的优势**:
- 更换数据库只需实现新的 Adapter,业务逻辑不变
- 更换框架只影响外层,核心逻辑不受影响
- 业务逻辑清晰,易于理解和演进

### 1.4 思想演进

**从过程式到对象式的演进**:
- 传统架构: 业务逻辑在 Service 层,领域对象是贫血模型(只有数据,没有行为)
- 端口驱动架构: 业务逻辑在领域对象中,富领域模型(数据+行为)

**这代表了软件工程思想的重要转折**:
- 从"数据+函数"到"对象(数据+行为的封装)"
- 从"技术驱动业务"到"业务独立于技术"
- 从"向外依赖"到"依赖反转"

### 1.5 权衡分析

**何时使用传统架构**:
- 简单 CRUD 应用,业务逻辑极少
- 团队不熟悉依赖反转和接口设计
- 项目生命周期短,无需长期演进
- **权衡**: 选择"简单"而放弃"可演进性"

**何时演进到端口驱动架构**:
- 业务逻辑变得复杂
- 需要高单元测试覆盖率
- 可能更换技术栈
- 长期维护项目
- **权衡**: 投入"初始复杂度"以换取"长期可维护性"

## 2. DDD vs Smart Domain

### 2.1 完整 DDD 的战术与战略

**战术设计**(Tactical Design):
- 实体(Entity)、值对象(Value Object)、聚合(Aggregate)、聚合根(Aggregate Root)
- 领域服务(Domain Service)、仓储(Repository)、工厂(Factory)
- 领域事件(Domain Event)

**战略设计**(Strategic Design):
- 限界上下文(Bounded Context)
- 上下文映射(Context Mapping)
- 通用语言(Ubiquitous Language)

**完整 DDD 的价值**:
- 系统性地治理复杂度
- 团队与业务专家统一语言
- 清晰的系统边界

**完整 DDD 的成本**:
- 学习曲线陡峭,需要持续领域建模
- 实施成本高,需要团队全员理解
- 可能过度设计,引入不必要的复杂度

### 2.2 Smart Domain 的务实简化

**保留的核心**:
- 富领域模型: 业务逻辑封装在领域对象中,避免贫血模型
- 业务逻辑与数据统一

**简化的部分**:
- 不强制执行聚合根、值对象的严格定义
- 可能不使用限界上下文等战略设计
- 灵活选择 DDD 战术模式,按需应用

**Smart Domain 的权衡**:
- 获得富领域模型的核心价值
- 降低学习曲线和实施成本
- 灵活性更高,但可能缺乏 DDD 的系统性

### 2.3 成本与收益对比

| 维度 | DDD | Smart Domain |
|------|-----|-------------|
| 学习成本 | 高(需要理解大量概念) | 中(核心概念即可) |
| 实施成本 | 高(需要持续领域建模) | 中(灵活按需) |
| 业务复杂度治理 | 优秀(系统性方法) | 良好(核心价值) |
| 团队要求 | 高(需要领域建模能力) | 中(基本 OOP 即可) |
| 过度设计风险 | 高 | 低 |
| 长期收益 | 高(复杂业务) | 中(中等复杂度) |

### 2.4 何时选择哪个

**选择完整 DDD**:
- 业务复杂度极高(如金融核心、复杂电商规则)
- 业务规则频繁变更
- 长期维护项目(5年以上)
- 团队有领域建模能力或愿意投入学习
- **典型场景**: 银行核心系统、保险理赔系统、复杂订单系统

**选择 Smart Domain**:
- 业务复杂度中等
- 需要避免贫血模型,但完整 DDD 过于复杂
- 团队 DDD 经验有限
- 快速迭代的项目
- **典型场景**: 中型电商、SaaS 应用、内部管理系统

**权衡本质**:
- DDD: 选择"完整性和系统性"但接受"高学习成本"
- Smart Domain: 选择"务实和灵活"但放弃"DDD 的深度"

### 2.5 演进路径

**渐进式采用 DDD**:
1. 开始: 传统分层架构 + 贫血模型
2. 第一步: 引入富领域对象,实现 Smart Domain
3. 第二步: 必要时引入聚合、值对象等战术模式
4. 第三步: 如果系统规模扩大,引入限界上下文等战略设计

**这种渐进式方法的优势**:
- 降低风险,逐步验证价值
- 团队逐步学习,而非一次性投入
- 避免过度设计,按需引入复杂度

## 3. 模块化单体 vs 微服务

### 3.1 核心差异

| 维度 | 模块化单体 | 微服务 |
|------|-----------|--------|
| 部署单元 | 单一应用 | 多个独立服务 |
| 模块通信 | 进程内调用 | 网络调用(REST/gRPC) |
| 数据库 | 共享数据库(逻辑分离) | 独立数据库(Database per Service) |
| 事务 | 本地事务(ACID) | 分布式事务(Saga,最终一致性) |
| 部署协调 | 需要协调(整体发布) | 独立部署 |
| 扩展粒度 | 整体扩展 | 服务级扩展 |
| 故障隔离 | 差(单点故障) | 好(服务级隔离) |
| 技术栈 | 统一 | 可异构 |

### 3.2 发布独立性的权衡

**微服务的优势**:
- 每个服务独立发布,不影响其他服务
- 不同服务可以有不同的发布周期
- 发布风险低(只影响单个服务)
- 支持灰度发布、金丝雀发布

**微服务的代价**:
- 需要成熟的 CI/CD 流水线
- 需要服务版本管理和兼容性保证
- API 变更需要向后兼容或版本控制
- 跨服务变更需要协调多个服务的发布

**模块化单体的特点**:
- 所有变更在同一次发布中生效
- 无需担心服务间兼容性
- 发布协调成本低(同一个团队)
- 但发布风险相对较高(影响整个应用)

**权衡分析**:
- 如果不同模块/服务的发布频率差异大(如订单服务每天发布,支付服务每周发布),微服务的独立部署价值显著
- 如果发布频率相近且可协调,模块化单体的简单性更有价值

### 3.3 运维成本的深度对比

**模块化单体的运维**:
- 部署: 1个应用,1个数据库
- 监控: 标准的应用监控
- 日志: 集中在一个应用内
- 调试: 在单一进程中,容易定位问题
- 故障恢复: 重启应用

**微服务的运维**:
- 部署: N个服务,N个数据库,需要容器编排(Kubernetes)
- 监控: 需要分布式追踪(Jaeger/Zipkin)、服务拓扑、聚合监控
- 日志: 需要集中式日志(ELK/Loki)、分布式日志追踪
- 调试: 需要跨服务追踪请求链路,复杂度高
- 故障恢复: 需要服务发现、健康检查、自动重启、熔断

**运维团队规模对比**:
- 模块化单体: 1-2 个运维人员即可
- 50 个微服务: 需要 5-10 个 SRE/DevOps,或专门的平台团队

**基础设施成本**:
- 模块化单体: 几台应用服务器 + 数据库集群
- 微服务: Kubernetes 集群 + 服务网格 + API Gateway + 消息队列 + 分布式追踪 + 集中式日志 + 监控系统

**洞察**: 微服务的运维成本往往被严重低估。很多团队在采用微服务后发现,运维成本超过了研发成本。

### 3.4 Conway 定律的影响

**Conway 定律**: 系统架构会反映组织的沟通结构。

**微服务与组织结构**:
- 每个服务由独立的团队负责
- 团队全栈负责(开发、测试、部署、运维)
- 团队自治,减少跨团队协调
- **前提**: 组织已经是多团队结构,且每个团队职责明确

**模块化单体与组织结构**:
- 整个应用由一个大团队或多个小团队共同负责
- 需要团队间协调发布
- 适合中型团队(10-100人)

**反 Conway 定律的风险**:
- 如果组织是单一团队,采用微服务会导致沟通开销巨大
- 如果组织已经是多团队结构,使用模块化单体会导致协调地狱

**洞察**: 架构应该反映组织现状,而非期望的组织形态。先有多团队结构,再考虑微服务,而非反过来。

### 3.5 演进时机与策略

**从模块化单体演进到微服务的时机**:
1. **团队规模**: 超过 50 人,多个独立产品团队
2. **扩展需求**: 不同模块的扩展需求显著不同
3. **发布频率**: 不同模块的发布频率差异大,协调成本高
4. **平台成熟度**: Kubernetes、服务网格、可观测性等基础设施已就绪
5. **技术异构性**: 需要在不同模块使用不同技术栈

**演进策略**(Strangler Fig Pattern):
- 不要"大爆炸"式重写
- 从边界清晰、变更频繁的模块开始拆分
- 逐步迁移,保持系统可用
- 评估每次拆分的收益

**何时不应该演进**:
- 团队规模未达到 50 人
- 平台能力不足
- 模块化单体运行良好,无明显瓶颈
- **记住**: 不演进也是一种选择

**权衡本质**:
- 微服务: 用"分布式复杂度"换取"部署独立性和扩展灵活性"
- 模块化单体: 用"部署耦合"换取"简单性和数据一致性"

## 4. 事件驱动/CQRS/事件溯源

### 4.1 一致性权衡

**同步调用(传统架构)**:
- 强一致性(ACID)
- 实时反馈
- 简单直观

**异步事件驱动**:
- 最终一致性
- 延迟反馈
- 复杂但解耦

### 4.2 CQRS 的读写分离

**为什么需要 CQRS**:
- 读取和写入的需求不同
- 读取: 需要复杂查询、聚合、分页,性能敏感
- 写入: 需要业务逻辑验证、事务保证

**CQRS 的解决方案**:
- 命令端(写): 使用规范化的领域模型,保证业务规则
- 查询端(读): 使用反规范化的视图模型,优化查询性能
- 通过事件同步: 命令端发布事件,查询端订阅事件更新视图

**权衡**:
- 优势: 读写独立优化和扩展
- 代价: 最终一致性,读取的数据可能不是最新的

### 4.3 事件溯源的可审计性

**传统方式**:
- 只存储当前状态
- 变更历史通过审计日志(Audit Log)记录
- 难以重建历史状态

**事件溯源**:
- 存储所有状态变更事件
- 当前状态由事件重放得出
- 可以重建任意时间点的状态

**优势**:
- 完整的审计跟踪
- 支持"时间旅行"调试
- 支持事件重放和数据修复

**代价**:
- 存储成本高(所有历史事件)
- 查询当前状态需要重放(需要快照优化)
- 事件模型设计复杂
- 事件版本管理困难

### 4.4 复杂度权衡

**引入的额外复杂度**:
- 事件建模和设计
- 最终一致性的处理
- 事件版本和兼容性
- 分布式追踪和调试

**是否值得**:
- 如果需要高度解耦: 值得
- 如果需要完整审计: 值得
- 如果读写比例悬殊: CQRS 值得
- 如果只是简单 CRUD: 不值得

## 5. 思想维度对比

### 5.1 设计哲学对比

| 架构 | 核心哲学 | 思想来源 |
|------|---------|---------|
| 分层架构 | 关注点分离(技术维度) | 传统软件工程 |
| MVC | 关注点分离(职责维度) | Smalltalk-80 |
| DDD | 业务复杂度用领域模型治理 | Eric Evans |
| 六边形/整洁 | 依赖反转,业务独立于技术 | SOLID 原则 |
| 微服务 | 服务自治,Conway 定律 | SOA 演进,云原生 |
| 事件驱动 | 异步解耦,最终一致性 | 消息驱动系统 |
| 模块化单体 | 性价比,务实平衡 | 对微服务的反思 |

### 5.2 思想演进脉络

**过程式 → 对象式**:
- 从"数据+函数分离"到"数据+行为封装"
- 从贫血模型到富领域模型
- 代表: 分层架构 → DDD

**向外依赖 → 依赖反转**:
- 从"业务依赖技术"到"技术适配业务"
- 从"紧耦合"到"松耦合"
- 代表: 分层架构 → 六边形架构

**集中式 → 分布式**:
- 从"单体应用"到"服务自治"
- 从"强一致性"到"最终一致性"
- 代表: 单体 → 微服务

**微服务热潮 → 理性回归**:
- 从"分布式优先"到"性价比优先"
- 从"过度拆分"到"合理粒度"
- 代表: 微服务 → 模块化单体

### 5.3 权衡的本质

**复杂度 vs. 灵活性**:
- 简单架构: 低复杂度,低灵活性
- 复杂架构: 高复杂度,高灵活性
- 关键: 复杂度是否与问题匹配

**性能 vs. 一致性**(CAP 定理):
- 分布式系统无法同时保证一致性、可用性、分区容错性
- 必须在 CP 或 AP 之间选择
- 微服务选择 AP(可用性+分区容错性),接受最终一致性

**耦合 vs. 性能**:
- 紧耦合: 高性能(进程内调用),低灵活性
- 松耦合: 低性能(网络调用),高灵活性
- 模块化单体 vs. 微服务

**完整性 vs. 务实性**:
- 完整 DDD: 系统性,但成本高
- Smart Domain: 务实,但缺乏深度
- 完美主义 vs. 够用就好

## 6. 权衡与失败模式分析

### 6.1 常见反模式

**贫血模型**:
- 现象: 领域对象只有 getter/setter,业务逻辑在 Service 层
- 原因: 对 OOP 理解不足,习惯于过程式编程
- 后果: 业务逻辑分散,难以复用和维护
- 解决: 引入富领域模型(Smart Domain/DDD)

**分布式单体**:
- 现象: 采用微服务架构,但服务间紧密耦合,必须一起部署
- 原因: 服务边界划分不合理,过度的同步调用
- 后果: 既有微服务的复杂度,又失去了独立部署的优势
- 解决: 重新划分服务边界,引入事件驱动解耦

**过度微服务化**:
- 现象: 服务拆分过细,大量服务间调用
- 原因: "微服务即正义"的误解,盲目追求"小"
- 后果: 运维成本激增,性能下降,调试困难
- 解决: 合并服务,形成合理粒度的服务,或回归模块化单体

**错误拆分**:
- 现象: 服务边界与业务边界不一致,大量跨服务事务
- 原因: 按技术层次拆分,而非按业务能力拆分
- 后果: 数据一致性难以保证,大量 Saga 事务
- 解决: 用 DDD 的限界上下文指导服务拆分

### 6.2 成本分解

**认知成本**:
- 低: 分层架构、MVC
- 中: 模块化单体、Smart Domain
- 高: DDD、六边形架构、微服务、事件驱动

**治理成本**:
- 低: 单体架构,统一治理
- 高: 微服务,去中心化治理,需要服务目录、API 管理等

**运维成本**:
- 低: 单体架构
- 中: 模块化单体
- 高: 微服务、服务网格

**观测成本**:
- 低: 单体架构,标准监控
- 高: 微服务,需要分布式追踪、聚合日志、服务拓扑

**数据一致性成本**:
- 低: 单体架构,本地事务
- 高: 微服务,Saga 模式,最终一致性处理

---

## 7. 决策表与情境示例

### 情境 1: 初创公司,5 人团队,快速试错

**推荐架构**: MVC 或分层架构

**理由**:
- 简单快速,无需学习复杂架构
- 运维成本低
- 可以专注于业务验证,而非架构

**不推荐**: 微服务、DDD
- 过度工程,运维成本超过团队承受能力

---

### 情境 2: 中型电商,50 人团队,业务复杂

**推荐架构**: 模块化单体 + 六边形架构 + Smart Domain

**理由**:
- 模块化单体: 运维简单,数据一致性好
- 六边形架构: 模块边界清晰,可测试性高
- Smart Domain: 治理业务复杂度,但不过度

**演进路径**: 必要时可以将部分模块演进为微服务

---

### 情境 3: 大型电商,200 人团队,多产品线

**推荐架构**: 微服务 + DDD + 六边形架构

**理由**:
- 微服务: 支持多团队并行开发,独立部署
- DDD: 限界上下文指导服务拆分
- 六边形架构: 每个服务内部架构清晰

**前提**: 平台能力成熟(Kubernetes、服务网格、可观测性)

---

### 情境 4: 金融核心系统,强一致性要求

**推荐架构**: 模块化单体 + DDD + 六边形架构

**理由**:
- 模块化单体: 本地事务,强一致性
- DDD: 治理复杂业务规则
- 六边形架构: 高可测试性,满足金融合规要求

**不推荐**: 微服务(除非业务规模极大)
- 最终一致性难以满足金融业务要求

---

## 结论

架构选型的核心是理解权衡:
1. **没有完美的架构**,只有在约束下的最优解
2. **依赖反转是现代架构的核心思想**,六边形架构和整洁架构广泛适用
3. **微服务不是银弹**,模块化单体是中型团队的更优选择
4. **业务复杂度优先用领域模型治理**,而非技术手段
5. **架构应该演进而来**,而非一次性设计
