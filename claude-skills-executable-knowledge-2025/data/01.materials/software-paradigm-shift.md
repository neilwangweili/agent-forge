## 核心内容

### 软件范式演进的三个阶段

#### 第一阶段: 指令式编程 (Imperative Programming)

**特征**:
- 明确的控制流程
- 逐步执行的指令序列
- 状态的显式管理
- 低级抽象

**代表语言**: 汇编、C、早期 Java

**开发者职责**:
- 详细描述"如何做"
- 管理内存和状态
- 控制执行流程

**局限性**:
- 代码冗长复杂
- 难以维护和理解
- 与问题领域的语义距离远

#### 第二阶段: 声明式编程 (Declarative Programming)

**特征**:
- 描述"做什么"而非"如何做"
- 隐藏实现细节
- 高级抽象
- 函数式或逻辑式

**代表技术**: SQL、正则表达式、React、配置即代码(IaC)

**开发者职责**:
- 描述期望的结果
- 定义约束和规则
- 交给系统优化执行

**突破**:
- 大幅提升表达力
- 更接近问题领域
- 减少样板代码

**局限性**:
- 仍需要学习特定语法
- 表达能力受限于语言设计
- 需要精确的形式化描述

#### 第三阶段: 面向提示词编程 (Prompt-Oriented Programming)

**特征**:
- 使用自然语言描述意图
- AI 理解并智能执行
- 极高级抽象
- 人机协同

**代表技术**: Claude Skills、Agent Blueprint、AI-assisted coding

**开发者职责**:
- 清晰描述目标和标准
- 提供必要的上下文
- 验证和优化结果

**突破**:
- 零学习成本(使用自然语言)
- 无限的表达能力
- AI 补全实现细节

**新的挑战**:
- 结果的不确定性
- 如何验证正确性
- 成本控制

### 提示词工程的三次范式转移

#### 第一次范式转移 (2020-2022): 从指令到上下文学习

**转变**: "Prompt" 不再仅仅是输入,而是一种"软编程"的手段。

**In-Context Learning (上下文学习)** 的黎明:
- 通过示例教会模型
- Few-shot、Zero-shot 提示
- Prompt 成为一种编程范式

#### 第二次范式转移: 从行为主义到认知主义

**转变**: 提示工程从"行为主义"(只关心输入输出)走向了"认知主义"(开始关注和引导中间过程)。

**Chain-of-Thought (思维链)** 的出现:
- 引导模型展示推理过程
- 通过中间步骤提升准确性
- 从"黑盒"到"可解释"

**代表技术**:
- CoT (Chain-of-Thought)
- ReAct (Reasoning + Acting)
- Tree of Thoughts

#### 第三次范式转移 (2025-): 从手工炼制到系统生成

**转变**: 提示工程师的工作重心,将从"炼制"单个提示,转向设计和维护整个提示生成和优化系统。

**动态优化技术的崛起**:
- 从静态提示到动态生成
- 从经验驱动到工程化范式
- 从手工调优到自动优化

**2025 年新趋势**:
- **自动提示优化**: AI 系统自动调整提示以提升性能
- **提示模板系统**: 类似 Claude Skills 的模块化提示管理
- **元提示** (Meta-Prompts): 生成提示的提示

### Claude Skills 作为新范式的代表

#### 从临时抱佛脚到职业技能树

**传统提示词工程**:
- 每次对话都要重新解释需求
- 知识和经验分散在聊天记录中
- 无法系统化复用

**Skills 系统**:
- 可以随时装载的专业能力模块
- 系统化、可复用的知识封装
- "职业技能树"而非"临时抱佛脚"

#### 从单次对话到持久能力

**传统 AI 对话**:
```
用户每次对话:
"请按照我们公司的代码规范..."
"报告格式要求是..."
"记得要..."
```

**Skills 范式**:
```
安装一次: company-code-standards.skill
之后: Claude 自动应用标准,无需重复
```

**核心转变**: 从"会话级"能力到"持久化"能力

#### 从提示词到可执行知识

**提示词 (Prompts)**:
- 临时性的指令
- 会话级生命周期
- 无结构化组织

**Skills (可执行知识)**:
- 持久化的能力包
- 可安装、可分享、可版本控制
- 模块化、层次化组织

**范式意义**: 知识从"对话"升华为"软件"

### AgentForge: 声明式架构的集大成者

#### AI 正在改变架构的基本假设

从 AgentForge 架构文档的开篇论述:

**传统软件架构的基本假设**:
- 系统的行为通过代码精确定义
- 运行时环境机械地执行这些定义
- 从《设计模式》到《企业应用架构模式》,半个多世纪的软件工程智慧都建立在这个基本假设之上

**AI 时代的新假设**:
- 系统的行为不再由代码精确规定,而是由自然语言描述的意图和标准引导
- 运行时环境不再是被动的执行器,而是主动的理解者和决策者
- 传统架构模式中的许多概念(接口、抽象类、依赖注入)开始显得过于机械和低层

**新的架构概念浮现**:
- Agent Blueprint (智能体蓝图)
- 智能运行时 (Intelligent Runtime)
- 数据驱动行为 (Data-Driven Behavior)

#### 从指令式到声明式的完全转变

**传统指令式代码**:
```python
def collect_data(org_id, year, month):
    url = f"https://api.example.com/org/{org_id}"
    response = requests.get(url)
    data = response.json()
    # ... 详细的数据处理逻辑
    save_to_file(data, f"data/{year}-{month}/{org_id}.json")
```

**AgentForge 声明式蓝图**:
```markdown
## 你的角色
你是数据采集专家

## 任务
访问 {ORGANIZATION_ID} 在 {YEAR}-{MONTH} 的官网,
搜集所有活动信息

## 输出
将结构化数据保存到 data/{YEAR}-{MONTH}/raw/{ORG_ID}/activities.json

## 质量标准
- 数据完整性
- 来源可追溯
- 格式符合 activity-record-template.json
```

**根本区别**:
- 代码描述"如何做",蓝图描述"做什么"
- 代码是精确的,蓝图是指导性的
- 代码被机械执行,蓝图被智能理解

#### 知识工程的五个支柱

AgentForge 提出的知识工程框架:

**1. 问题导向 (Problem-Oriented)**
- 基于真实研究需求
- 明确"解决什么问题"和"为何解决"
- 是所有工作的根本起点

**2. 意识形态 (Ideology)**
- 选择价值观、理论视角或分析框架
- 指导 AI 的思考与表达
- 不同框架导致不同结论

**3. 信息储备 (Information Reserve)**
- 高质量信息储备是基础
- 通过数据采集和 Reference Data 建立
- 支撑知识的应用

**4. 理论方法 (Theoretical Methods)**
- 解决问题的理论及方法论
- 研究的核心
- 在 Agent Blueprint 中具体化

**5. 表现形式 (Presentation Form)**
- 最终成果的呈现方式
- 格式、结构、写作风格
- 在 style-guide 中定义

**核心洞察**: AgentForge 不是简单的"提示词工程",而是"知识工程"

### 智能运行时: 从被动执行到主动决策

#### 传统运行时 vs 智能运行时

| 维度 | 传统运行时 | 智能运行时 |
|------|-----------|-----------|
| **输入** | 字节码/源代码 | 自然语言 Agent Blueprint |
| **执行方式** | 机械执行指令序列 | 理解意图,智能选择执行方式 |
| **决策能力** | 无(完全由代码决定) | 强(可在执行时做出适应性决策) |
| **错误处理** | 抛出异常,停止执行 | 理解错误情境,尝试恢复或降级 |
| **优化** | JIT 编译等低层优化 | 策略选择、工具组合等高层优化 |
| **确定性** | 高(相同输入→相同输出) | 中(相同 Blueprint 可能有不同执行路径) |

#### 关键引用的深度分析

来自 AgentForge 用户的观察:

> "我自己写的 bash 或 Python 代码,不会比 Claude Code 执行到那儿的时候选择的指令方法更好。"

**为什么这是真的？**

**原因 1: 信息不对称**
- 开发时: 只知道任务一般性描述,必须做各种假设
- 执行时: Claude Code 知道具体要处理的数据,知道当前环境状态,知道前序步骤结果

**原因 2: 智能的层次不同**
- 预写代码: 只能包含开发者预见的逻辑分支
- Claude Code 智能: 可以处理未预见情况(例如网站结构改变,分析新结构提取信息)

**原因 3: 工具选择的灵活性**
- 预写代码: 必须提前决定用什么工具
- Claude Code: 根据实际情况选择最优工具组合

**原因 4: 质量感知**
- 预写代码: 只能检查格式正确性
- Claude Code: 可以评估内容质量(语义层面)

**深刻洞察**: 将决策推迟到执行时是一种强大的架构模式

### 软件的终结?

#### 研究主题中的哲学问题

> "如果软件的本质是知识,那么传统意义上的'软件'是否还存在?未来的方向是否是 AI 智能体?这是否意味着我们正在经历从'面向对象编程'到'面向提示词编程'的范式转移?"

#### 软件的重新定义

**传统定义**: 软件是一组精确的指令,告诉计算机如何执行任务。

**新的定义可能**: 软件是一组知识和标准,由 AI 理解并智能执行以完成任务。

**核心差异**:
- 从"精确指令"到"知识和标准"
- 从"机械执行"到"智能执行"
- 从"开发者决定一切"到"AI 运行时决策"

#### 软件边界的模糊化

**传统软件的清晰边界**:
```
开发阶段: 编写代码
    ↓
编译/部署: 打包为可执行文件
    ↓
运行阶段: 机械执行
```

**AI 时代的模糊边界**:
```
设计阶段: 编写 Agent Blueprint
    ↓
运行阶段: AI 理解、决策、执行
    ↓
(没有明确的"编译"阶段)
(开发和运行的边界模糊)
```

**关键问题**:
- Agent Blueprint 是"代码"吗?
- AI 的理解和决策是"编译"还是"执行"?
- 如果每次执行都可能不同,是否还是"软件"?

#### 从编程到提示的连续谱

```
传统编程 ←----------------------→ 纯粹提示
    |         |         |         |
  汇编      C/Java    DSL    Agent Blueprint
    |         |         |         |
精确控制  抽象控制  领域表达  自然语言描述
    |         |         |         |
  确定性   确定性    确定性    智能执行
```

**关键观察**: 不是非此即彼,而是一个连续谱。不同任务选择不同位置。

#### 未来展望: 混合范式

**可能的未来**:
- 核心逻辑: 传统代码(确定性、性能)
- 业务规则: DSL 或配置(灵活性)
- 智能决策: Agent Blueprint(适应性)

**不是替代,而是融合**: AI 不会完全替代传统编程,而是在合适场景补充和增强。

### 范式转移的驱动力与阻力

#### 驱动力

**1. AI 模型能力突破**
- 大语言模型的理解和生成能力
- 从"回答问题"到"执行任务"
- 从"对话"到"编程"

**2. 复杂性管理需求**
- 软件系统越来越复杂
- 传统方法难以应对
- 需要更高层次的抽象

**3. 开发效率压力**
- 市场对速度的要求
- 开发者短缺
- 降低编程门槛的需求

**4. 知识工作者的需求**
- 非程序员也需要"编程"
- 领域专家直接定义系统行为
- 民主化的软件开发

#### 阻力

**1. 确定性的丧失**
- AI 执行结果不完全可预测
- 难以形式化验证
- 关键系统的顾虑

**2. 成本问题**
- AI 推理的计算成本
- Token 消耗的费用
- 相比传统代码执行的高成本

**3. 信任问题**
- 对 AI 决策的信任
- 出错时的责任归属
- 监管和合规要求

**4. 技能转型**
- 传统程序员的技能转型
- 教育体系的适应
- 行业惯性

#### 适用场景的清晰划分

**适合 AI 智能体范式**:
- 信息处理密集型任务
- 规则和标准清晰但实现复杂
- 执行频率不高(批处理)
- 质量和灵活性重于成本和速度

**仍适合传统编程**:
- 实时系统
- 高频交易
- 需要绝对确定性的场景
- 计算密集型任务

## 采集者注释

### 核心洞察

1. **三个阶段清晰可辨**: 指令式 → 声明式 → 面向提示词,每个阶段都是抽象层次的跃升

2. **2025 年是转折点**: 提示词工程从实验走向工程化,从手工走向系统化

3. **智能运行时是关键**: 不仅是工具进步,更是架构思维的根本转变

4. **软件边界确实在模糊**: Agent Blueprint 既是知识也是程序,挑战了传统"软件"定义

5. **不是非此即彼**: 不同范式适合不同场景,未来是混合架构

### 与研究主题的深度关联

**支持"软件本质转变"洞察**:
- 从"精确执行指令"到"可被理解与执行的知识"
- Brooks 的"本质复杂性"被 AI 部分解决
- 但引入了新的复杂性(不确定性、信任)

**支持"开发范式转变"洞察**:
- 从"指令式编程"到"声明式知识定义"
- 提示词工程的三次范式转移清晰展现演进路径
- Skills 系统是"面向提示词编程"的具体实现

**支持"协作模式转变"洞察**:
- 从"共享代码仓库"到"共享智能体蓝图"
- Agent Blueprint 作为可执行的协作标准
- 降低了协作门槛,提升了知识传递效率

### 待深入的哲学问题

1. **存在论**: 如果 Agent Blueprint 是"软件",那么"软件"的本质是什么?

2. **认识论**: AI 理解的"知识"与人类理解的"知识"是否相同?

3. **伦理学**: 当 AI 做出运行时决策,谁承担责任?

4. **社会学**: 这种范式转移如何改变软件工程师的角色和身份?

### 实践观察

通过 AgentForge 案例,我们看到:
- 声明式架构不是理论,而是可行的实践
- 效率提升是显著的(2 小时 vs 1-2 个月)
- 但也有明确的边界(不适合实时、高频场景)

这种务实的观察为研究提供了重要的现实锚点。
